A model that reads well is not one you can trust to act

Why I keep the model on reading documents and put the decisions in plain code.

When I started using language models on business documents, I assumed the hard part would be getting the model to read them. It was the opposite. Models read invoices, forms and contracts well now. The hard part is deciding what happens next.

Two jobs hiding in one prompt

A prompt like "read this invoice and approve it if it looks fine" asks for two different things. One is extraction: what does the document say? The other is judgment: is it safe to act on it?

If you mix them, you cannot tell which one failed. When something goes wrong, you do not know if the model misread a number or made a bad call about a number it read correctly.

Keep the model on reading

I let the model do what it is good at, which is turning messy documents into fields. Then plain code does the judging. Do the totals add up? Does this ID exist in our system? Have we seen this exact document before? Is the tax in the range we expect?

These checks are boring on purpose. You can test them, you can read them, and you can explain them to the person in finance or operations who owns the outcome. "The model felt confident" is not an explanation anyone can sign off on.

Use confidence to route, not to decide

Models can report how sure they are about each field. That number is useful, but it is not the truth. I use it for routing: if the checks pass and confidence is high, the document goes through. If not, it goes to a person.

The model can still help the person. A short note on why something was flagged, in plain words, saves them from hunting through the document.

Start with the checks

A practical way to begin: write down what a careful human clerk checks before they act on this kind of document. That list is your set of checks. Then work backwards and ask what the model has to hand over for each one.

This also tells you early where the project is risky. If a check needs information the model cannot reliably produce, you find out in week one, not after launch.

The bar that matters

People ask how often the model is right. I care more about a different question: when it is wrong, does the system notice? A model that is right most of the time and a system that catches the rest is something you can run without watching it all day.
